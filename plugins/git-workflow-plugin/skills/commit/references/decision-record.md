# 変更内容と意思決定の記録（コミット本文）

コミット本文に変更内容と意思決定を残すための記述例集。詳細度は `.commit-template.yml` の `decision_record.mode` で制御する。

## なぜコミット本文なのか

| 記録先 | 問題 |
|:-|:-|
| `docs/plans/` などのプランファイル | 完了後も検索に引っかかりノイズになる。仕様変更時に直すか否かが曖昧で陳腐化する |
| `plans/archive/` への退避 | 退避の手間が増えるだけで、検索ノイズ・陳腐化は解決しない |
| **コミット本文** | 差分と 1 対 1。追記のみで陳腐化しない。`git log` で検索できる。掃除不要 |

## mode 別の記述例

### off

本文なし。subject のみ。

```
✏️ [Typo]: READMEのインストール手順の誤字を修正
```

### minimal

変更内容 / 採用理由。採用理由は 1〜3 行。

```
🩹 [Quick Fix]: ログ出力のタイムスタンプをUTC固定に変更

変更内容:
- ロガー初期化のタイムゾーン設定をUTC固定に変更

採用理由:
CIとローカルでログの時刻がずれて突き合わせできなかったため、
実行環境のTZに依存しないUTC固定にした。
```

### standard（デフォルト）

変更内容 / 背景 / 採用理由 / トレードオフ。

```
♻️ [Refactoring]: #45 認証トークンの検証をAuthTokenVerifierに集約

変更内容:
- ミドルウェア・APIハンドラ・バッチのトークン検証をAuthTokenVerifierに集約
- 検証失敗を真偽値ではなく例外型で返すよう変更

背景:
トークン検証がミドルウェア・APIハンドラ・バッチの3箇所に複製されており、
有効期限のリーウェイ設定だけが1箇所で古いまま残っていた。

採用理由:
共通関数への切り出しではなくクラスに集約した。検証には公開鍵のキャッシュと
いう状態が伴い、関数のままでは呼び出し側でキャッシュを持ち回る必要があった
ため。

トレードオフ:
検証の失敗理由が例外型で返るようになり、呼び出し側のcatchが型で分岐できる。
既存の真偽値を返すAPIは残していないので、外部から直接呼んでいる箇所があれば
コンパイルエラーになる（リポジトリ内は全て移行済み）。
```

### detailed

変更内容 / 背景 / 採用理由 / 代替案 / トレードオフ / 参考。

```
✨ [New Feature]: #210 セッションストアをRedisに移行

変更内容:
- セッションストアをインメモリからRedisに移行
- セッションTTLをRedisのキー有効期限で管理するよう変更

背景:
アプリを複数インスタンスに水平展開したが、セッションがインメモリのため
ログイン直後にリクエストが別インスタンスへ振られるとログアウト扱いになる。
ロードバランサのスティッキーセッションで暫定回避していたが、デプロイの
ローリング更新のたびに全ユーザがログアウトしていた。

採用理由:
外部ストアとしてRedisを採用した。既にレートリミット用途で運用実績があり、
新規のミドルウェアを増やさずに済むため。TTLをセッション有効期限に対応
させられる点も要件に合う。

代替案:
- DB（PostgreSQL）にセッションテーブルを持つ: 追加ミドルウェアは不要だが、
  リクエストごとの読み書きが接続プールを圧迫する。ピーク時のプール枯渇が
  既に別件で発生しているため却下
- JWTでステートレス化: ストア自体が不要になるが、即時失効の要件
  （管理者による強制ログアウト）を満たせないため却下。失効リストを持つと
  結局ストアが必要になる
- スティッキーセッション継続: ローリング更新時のログアウトが解決しないため却下

トレードオフ:
Redisが単一障害点になる。停止時はログインが全面的に不可となるため、
可用性はマネージドサービスのフェイルオーバーに依存する形になった。
セッション読み取りに1リクエストあたり約1msのネットワーク往復が加わる。
既存セッションは移行せず、デプロイ時に全ユーザが1度ログアウトする。

参考:
Refs #210
Relates to #187
```

## NG 例

### 意思決定セクションで「何をしたか」を繰り返している

「何をしたか」は変更内容に書く。背景・採用理由で言い換えても情報が増えない。

```
変更内容:
- validateUser関数を追加

背景:
UserService.tsを変更した。

採用理由:
validateUser関数を追加し、既存の処理から呼び出すようにした。
```

**修正:** 背景には変更が必要になった経緯を、採用理由にはなぜ切り出す必要があったのか（重複していた／テストできなかった等）・なぜその形（関数／クラス／別モジュール）を選んだのかを書く。

### 却下理由のない代替案

「検討した」だけでは、次に同じ案を検討する人の判断材料にならない。

```
代替案:
- GraphQLの採用
- BFFの新設
```

**修正:** 各案に却下理由を必ず添える。将来再検討しうる条件があればそれも書く（例: 「クライアントが3つを超えたら再検討」）。

### トレードオフを書かずに利点だけ並べる

```
トレードオフ:
パフォーマンスが向上し、コードも読みやすくなった。
```

**修正:** 何を犠牲にしたかを書く。犠牲が本当にないなら、影響範囲（互換性・運用・移行）を具体的に書く。

## 判断基準

迷った場合は以下を基準にする。

> 「半年後にこの変更を revert しようとした人が、`git log` だけで
> 『なぜこうなっているか』『revert して壊れるものは何か』を判断できるか？」

判断できないなら本文が足りていない。

## 履歴の追い方

```bash
git log --grep="代替案"                # 代替案を検討したコミットを探す
git log --grep="採用理由" -p               # 判断理由と差分を並べて読む
git log -S"AuthTokenVerifier"          # ある識別子が増減したコミットを探す
git log --follow -p -- <file>          # ファイルの変遷を判断理由込みで追う
git log --format=%B <base>..HEAD       # PR作成時にブランチ内の判断を集める
```

見出し文字列は `decision_record.sections[].title` に揃えて表記ゆれを作らないこと。`--grep` の検索性はそこに依存している。
