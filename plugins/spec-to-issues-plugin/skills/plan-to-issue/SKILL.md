# Plan to Issue

実装プランをGitHub Issueとして登録するスキル。
軽い作業メモではなく、**意思決定の過程（検討した選択肢・決定理由）と実装方針**をしっかり記録する Design Doc / RFC 寄りの厚いフォーマットを使う。

想定する開発フロー:

```
1. プランを作る（plans/xxx.md 等。または対話で直接作成）
   ↓
2. このスキルでプランをGitHub Issueとして登録（1プラン = 1 Issue）
   ↓
3. 実装（発番されたIssue番号をコミットメッセージの #<Issue番号> に使う）
   ↓
4. 完了後にIssueをクローズ。プランファイルは削除してよい（内容はIssueに残る）
```

プラン Issue は「作業の手順書」ではなく「**どう作るかの判断の記録**」。closed になった後も意思決定の記録（ADR相当）として機能する。

---

## テンプレート解決の優先順位

Issue本文のフォーマットは以下の優先順位で解決する:

1. **`${CLAUDE_PLUGIN_ROOT}/.plugin-workspace/issues/plan-issue-template.md`**（プロジェクトカスタム）が存在する場合 → その構成を使用
2. **`references/plan-issue-template.md`**（ビルトインデフォルト）→ カスタムが存在しない場合のフォールバック

カスタムテンプレートを作りたい場合は、ビルトインをコピーして `${CLAUDE_PLUGIN_ROOT}/.plugin-workspace/issues/plan-issue-template.md` に配置し、セクションを増減する。

## ワークフロー

```
1. プランの入力（MDファイル読み込み or 対話ヒアリング）
   ↓
2. テンプレート解決とセクションへのマッピング
   ↓
3. メタ情報の補完（ベースブランチ・作業ブランチ・関連Issue）
   ↓
4. プレビュー提示とユーザー承認
   ↓
5. gh issue create でIssue登録
   ↓
6. 完了報告（Issue番号とコミットメッセージへの利用案内）
```

### Step 1: プランの入力

**引数でMDファイルパスが指定された場合**: ファイルを読み込み、内容を解析する。

**引数が省略された場合**: 対話でプラン内容をヒアリングする。最低限、以下を確認する:

1. やること一言（タイトル）
2. 背景・課題
3. 検討した選択肢と決定（選択肢が1つしかない場合はその旨を記録）
4. 実装方針の要点

### Step 2: テンプレートへのマッピング

解決したテンプレートのセクション構成に従い、プラン内容を各セクションに振り分ける。

**必須セクション**（欠けている場合はユーザーに確認して補完する）:

| セクション | 内容 |
|:--|:--|
| メタ情報 | ベースブランチ・作業ブランチ・関連Issue/PR |
| 背景 / 課題 | 現状の問題と経緯 |
| ゴール | 達成したいこと（完了条件がわかる粒度） |
| 検討した選択肢 | 案ごとの概要・良い点・悪い点 |
| 決定 | 採用案と理由（トレードオフの受け入れを明記） |
| 実装方針 | 全体設計・インターフェース設計・変更対象と影響範囲・実装の順序・採用する規約 |
| 検証方法 | どう確認したら完了とみなすか |

**任意セクション**（プランに情報がなければ省略してよい）:

| セクション | 内容 |
|:--|:--|
| 非ゴール（スコープ外） | 今回やらないこと |
| リスクと対策 | 想定リスクと緩和策 |
| 参考資料 | 調査リンク・関連ADR・参考実装 |

**マッピングのルール:**

- チェックリスト形式の「実装ステップ（作業手順）」は含めない。手順は実装時に判断する。「実装の順序」は着手順の方針レベルにとどめる
- 元プランに検討過程がない（結論だけ書かれている）場合、ユーザーに「検討した選択肢・却下理由」をヒアリングして補完する。不明なら「案A（採用）のみ検討」と正直に記録する
- 元プランの記述はできるだけ原文を保持し、勝手に要約・省略しない

### Step 3: メタ情報の補完

```bash
# ベースブランチの推定（デフォルトブランチ）
BASE_BRANCH=$(gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name')

# 作業ブランチの推定（現在のブランチ。ベースブランチと同一なら未定として扱う）
WORK_BRANCH=$(git branch --show-current)
```

- ベースブランチ: プランに明記があればそれを優先。なければ上記の推定値を提示して確認
- 作業ブランチ: 未定の場合は空欄にせず「未定（実装時に決定）」と記録してよい
- 関連 Issue / PR: プランに記載があれば転記。なければ「なし」

### Step 4: プレビューとユーザー承認

組み立てたIssueタイトル・ラベル・本文の全文をユーザーに提示し、承認を得る。
修正指示があれば反映して再提示する。**承認なしにIssueを作成しない。**

### Step 5: Issue登録

```bash
PLAN_URL=$(gh issue create \
  --title "[Plan] {やること一言}" \
  --body "{テンプレートに従って組み立てた本文}" \
  --label "type:plan")

PLAN_NUM=$(echo "$PLAN_URL" | grep -oE '[0-9]+$')
```

- ラベルは `type:plan` を必ず付与する。内容から判定できる場合は `area:*` / `size:*` ラベルも付与する（判定基準は `spec-to-issues` スキルと同一）
- `type:plan` ラベルが存在しない場合は `scripts/create-github-labels.sh` の実行を案内する

### Step 6: 完了報告

```
## プランIssue登録完了

- #{番号} [Plan] {タイトル}
- URL: {issue_url}

コミット時はこの番号を使用してください:
  <emoji> [<tag>]: #{番号} <subject>

実装完了・コミット後はプランファイルを削除して構いません（内容はIssueに残ります）。
```

## エラーハンドリング

| 状況 | 対応 |
|:--|:--|
| プランMDファイルが見つからない | エラー報告、正しいパスを確認 |
| プランMDファイルが空 | エラー報告、対話ヒアリングに切り替えるか確認 |
| 必須セクションの情報が不足 | ユーザーにヒアリングして補完（勝手に創作しない） |
| カスタムテンプレートが不正 | 報告してビルトインにフォールバック |
| `gh` CLIが未認証 | `gh auth login` の実行を案内 |
| `type:plan` ラベルが未作成 | `create-github-labels.sh` の実行を案内 |
| Issue作成APIエラー | エラー報告、1回リトライ、それでも失敗ならユーザーに確認 |
| 同名タイトルのopenなプランIssueが既に存在 | 重複の可能性を提示し、続行するか確認 |

## 禁止事項

- ユーザーの承認なしにIssueを作成しない
- 元のプランMDファイルを変更・削除しない（削除はユーザーが行う）
- プランに書かれていない決定理由や検討過程を創作しない
- `gh issue create` 以外の方法でIssueを作成しない
