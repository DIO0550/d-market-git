# Plan Issue Report

`plan-issue` スキルで登録したプラン Issue に、実装完了後の**振り返りコメント**を投稿するスキル。

プラン Issue は「どう作るかの判断の記録」。このスキルで「実際どうだったか」を同じ Issue に書き残すことで、**計画と実績・差分が 1 つの Issue に揃い**、閉じた後も意思決定の記録として完結する。

想定する開発フロー:

```
1. /plan-issue でプランをIssue登録
   ↓
2. 実装・コミット（#<Issue番号> を使用）
   ↓
3. このスキルで振り返りコメントを投稿（結果・想定と違った点・プランからの変更）
   ↓
4. Issueをクローズ
```

---

## テンプレート解決の優先順位

コメント本文のフォーマットは以下の優先順位で解決する:

1. **`${CLAUDE_PLUGIN_ROOT}/.plugin-workspace/issues/plan-report-template.md`**（プロジェクトカスタム）が存在する場合 → その構成を使用
2. **`references/plan-report-template.md`**（ビルトインデフォルト）→ カスタムが存在しない場合のフォールバック

カスタムテンプレートは `plan-template` スキルで生成できる（ビルトインをベースに対話でカスタマイズ）。

## ワークフロー

```
1. 対象プランIssueの特定
   ↓
2. プラン本文の読み込み（想定との比較材料）
   ↓
3. 実績情報の収集（会話の文脈・git履歴・ヒアリング）
   ↓
4. テンプレートに沿ってコメントを組み立て
   ↓
5. プレビュー提示とユーザー承認
   ↓
6. gh issue comment で投稿
   ↓
7. Issueクローズの確認
```

### Step 1: 対象プランIssueの特定

**引数でIssue番号が指定された場合**: その番号を使用する。

**引数が省略された場合**: 以下の順で自動検出を試みる。

```bash
# 1. 直近のコミットメッセージから #<番号> を抽出
git log --oneline -10 | grep -oE '#[0-9]+' | head -1

# 2. openなプランIssueの一覧から候補を提示
gh issue list --label "type:plan" --state open --json number,title
```

候補が複数ある場合や確信が持てない場合は、ユーザーに確認する。

### Step 2: プラン本文の読み込み

```bash
gh issue view {番号} --json title,body,labels
```

- `type:plan` ラベルが付いていることを確認する（付いていない場合は本当に対象かユーザーに確認）
- プラン本文の「決定」「実装方針」「メタ情報（作業ブランチ等）」「検証方法」を把握し、実績と比較する材料にする

### Step 3: 実績情報の収集

以下の材料から実績を組み立てる:

- **会話の文脈**: 直前まで実装作業をしていた場合、その内容（何を作ったか、何に詰まったか、方針変更）をそのまま材料にする
- **git履歴**: `git log`・PR情報から、コミット・PR番号・実際の作業ブランチを取得する
- **ヒアリング**: 上記で埋まらない項目（特に「想定と違った点」）はユーザーに確認する

**収集のルール:**

- 「想定と違った点」はプラン本文の記載（決定・実装方針・検証方法）と実際の差分を突き合わせて洗い出す。差分がなければ「なし（プラン通り）」と正直に書く
- 想定との差分や変更理由を創作しない。わからない項目はユーザーに聞く

### Step 4: コメントの組み立て

解決したテンプレートのセクション構成に従い、コメント本文を組み立てる。

| セクション | 必須 | 内容 |
|:--|:--|:--|
| 結果 | 必須 | ステータス・PR/コミット・実際の作業ブランチ |
| 想定と違った点 | 必須 | プラン時の想定と実際の差分・理由（なければ「なし」と明記） |
| プランからの変更 | 必須 | 決定・実装方針から変えた点と理由（なければ「なし」と明記） |
| 積み残し / フォローアップ | 必須 | やり残し・別Issue化したもの（なければ「なし」と明記） |
| 学び・メモ | 任意 | 次のプランに活かせること（なければ省略可） |

### Step 5: プレビューとユーザー承認

組み立てたコメント全文をユーザーに提示し、承認を得る。
修正指示があれば反映して再提示する。**承認なしにコメントを投稿しない。**

### Step 6: コメント投稿

```bash
gh issue comment {番号} --body "{テンプレートに従って組み立てた本文}"
```

### Step 7: Issueクローズの確認

コメント投稿後、Issueをクローズするかユーザーに確認する。

```bash
# 完了の場合
gh issue close {番号} --reason completed

# 積み残しがあり、Issueを開けたままにする場合はクローズしない
```

- 積み残しを別Issue化する場合は、クローズ前にフォローアップIssueの作成を提案してよい（作成は `gh issue create` で、ユーザー承認必須）

## エラーハンドリング

| 状況 | 対応 |
|:--|:--|
| プランIssueが特定できない | open な `type:plan` Issue の一覧を提示して選択してもらう |
| 指定されたIssueが存在しない | エラー報告、番号を確認 |
| 指定されたIssueに `type:plan` ラベルがない | 対象で合っているかユーザーに確認 |
| 指定されたIssueが既にclosed | その旨を提示し、コメントだけ投稿するか確認 |
| 実績情報が不足 | ユーザーにヒアリングして補完（勝手に創作しない） |
| カスタムテンプレートが不正 | 報告してビルトインにフォールバック |
| `gh` CLIが未認証 | `gh auth login` の実行を案内 |
| コメント投稿APIエラー | エラー報告、1回リトライ、それでも失敗ならユーザーに確認 |

## 禁止事項

- ユーザーの承認なしにコメントを投稿しない
- ユーザーの確認なしにIssueをクローズしない
- 想定との差分・変更理由を創作しない（わからなければユーザーに聞く）
- プランIssueの本文（元のプラン）を書き換えない（実績はコメントで追記する）
